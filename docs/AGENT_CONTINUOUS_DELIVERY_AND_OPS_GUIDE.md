# MOS 项目 Agent 持续开发 / 持续集成 / 持续运维指导书

## 1. 这份文档解决什么问题

这是一份给人看的操作手册，目标是让团队用 Agent 做三件事：

- 持续开发（快速改、改得稳）
- 持续集成（每次改动都可验证）
- 持续运维（上线后可观测、可回滚）

一句话原则：**小步快跑、每步可验、问题可回退**。

---

## 2. 先统一分工（人和 Agent 各做什么）

- 人负责：目标定义、风险边界、验收结果判断。
- Agent 负责：实现代码、执行检查、补文档、输出变更说明。
- 共同责任：任何改动都要能复现和回滚。

建议每次任务都带这 4 个输入：

1. 目标（要解决什么问题）
2. 约束（哪些文件不能动、是否允许改 DB）
3. 验收（接口/页面/性能要达到什么）
4. 风险点（权限、审计、发布影响）

---

## 3. 持续开发（CD：Continuous Development）流程

### Step 1：把任务切小

不要让 Agent 一次改“全项目”。推荐拆为 3 类：

- `收敛类`：去重复、抽公共函数、统一错误处理
- `性能类`：去 N+1、减少重复查询、减少大组件状态耦合
- `可读性类`：拆大文件、拆超长函数、统一命名

每次只做一个主题，PR 更容易审、回滚也简单。

### Step 2：给 Agent 一个“可执行提示”

建议模板：

```text
目标：
- 优化 <模块/页面/接口> 的 <重复/性能/可读性> 问题

硬约束：
- 必须遵守 docs/TOOL_INTEGRATION_STANDARD.md
- 前端禁止在 ToolDetail.vue / ToolManage.vue 写 tool.name 硬编码分支
- 列表必须后端分页 + 前端分页控件

验收：
- 代码修改完成
- powershell -File scripts/run-ci-tool-checks.ps1 通过
- frontend 下 pnpm run build 通过
- 给出手工冒烟路径
```

### Step 3：Agent 输出要有固定结构

- 改了什么（文件清单）
- 为什么这样改（收益和风险）
- 怎么验证（命令和结果）
- 如何回滚（最小回滚点）

---

## 4. 持续集成（CI）最小闭环

本项目建议把以下命令当作“最小门禁”：

1. 根目录运行：
   - `powershell -File scripts/run-ci-tool-checks.ps1`
2. `frontend` 目录运行：
   - `pnpm install --frozen-lockfile`（锁文件变化或首次）
   - `pnpm run build`

建议规则：

- PR 必须附上以上命令结果摘要。
- 任何失败先修复再合并，不带病进入主线。
- 评审重点先看：权限边界、分页、路由规范、中文用户提示是否一致。

---

## 5. 持续运维（Ops）实操建议

### 5.1 上线前检查清单

- 环境变量已确认（尤其 `DATABASE_URL`、部署环境相关变量）
- 工具可见性策略正确（内网/外网）
- 关键管理接口可用（工具状态、授权用户、使用记录）
- 回滚脚本或回滚步骤可执行
- 已按 `docs/templates/RELEASE_SCOPE_CHANGELOG_TEMPLATE.md` 填写发布范围（host/tool/mixed）与版本/变更记录
- 可先执行 `powershell -NoProfile -ExecutionPolicy Bypass -File "scripts/release-note-init.ps1" ...` 生成发布记录草稿再补充细项

### 5.2 上线后 30 分钟重点观察

- 错误率（4xx/5xx 是否异常升高）
- 关键接口耗时（是否出现明显抖动）
- 新功能使用日志是否正常入库（行为名称是否正确）
- 权限相关告警（是否出现误放行/误拦截）

### 5.3 出现问题时的处置顺序

1. 先止损：关闭高风险入口或回滚
2. 再定位：看最近变更 + 日志 + 权限链路
3. 最后修复：补最小修复并走同样 CI 流程

---

## 6. 建议的 Agent 例行节奏（每周）

- 每周一次“瘦身日”：
  - 清理重复代码
  - 抽公共能力
  - 补缺失文档
- 每周一次“性能巡检”：
  - 查慢查询
  - 查列表接口 N+1
  - 查前端超大组件
- 每周一次“发布演练”：
  - 按发布脚本走一遍
  - 验证可回滚

---

## 7. 给团队的落地建议（务实版）

- 不追求一次性大重构，先做“低风险高收益”项。
- 每次改动都让 Agent 产出“验证步骤 + 冒烟路径”。
- 任何跨模块改动，都要补一段“为何这么改”的说明，减少后续维护成本。
- 把重复问题持续记入待办，按优先级滚动清理，不攒技术债。

---

## 8. 本次改造可直接复用的收敛方向

- 后端统一 `count` 结果解析，减少重复样板。
- 列表接口优先做批量预取，避免 N+1。
- 前端统一 API 错误文案映射，减少登录/注册等页面重复逻辑。

这些属于“几乎无业务风险、能立刻见效”的第一批动作，建议优先长期坚持。
